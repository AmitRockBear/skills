# Browser and computer use

Use the active OpenAI native computer-use tool schema for ordinary pages, browser chrome and real docked extension sidebars. Use native controls for page actions and UI observations; Playwright may support browser lifecycle, download handling and passive telemetry. Keep the browser host, recording and downloaded bytes in a new task directory under the configured task output directory. On macOS, use the [virtual-display flow](local-display-test.md) by default. If using Playwright telemetry, keep one owned connection for download handling and click telemetry; a second CDP attachment can replace Chromium's download destination. If attaching for debugging, revalidate real saved download bytes before claiming success.

## Start and authenticate

1. Select the exact Chromium executable belonging to the tested Playwright installation; report its actual version and app bundle. Do not select the user's existing Chrome/Helium session by its displayed browser name.
2. On macOS, use the virtual-display flow by default and verify focus isolation on the actual machine. Use the bundled host as an alternative when foreground launch is acceptable. For that alternative, run the bundled host using Python with Playwright 1.56.0, or `uv run --script scripts/browser-session.py <new-browser-run> --url <assigned-local-url>`. Install the matching Chromium once with `uv run --with playwright==1.56.0 python -m playwright install chromium` if needed. Use `--executable <browser-executable>` for an existing pinned binary. Keep `browser.json` with the host PID, actual Chromium PID, fresh profile, version and loopback CDP port. CLI options `--width 1440 --height 1000` control the initial window.
3. For extension sidebar verification, build the extension from the tested revision and load the unpacked build with the virtual-display launch flags, or pass `--extension <absolute-unpacked-build-directory>` to the alternative host. Include only required extensions. A real docked side panel requires window capture; loading its HTML in a normal page is not equivalent. An OpenAI extension can be added through another `--extension`, but verify that it registers this owned browser rather than assuming the user's connected Chrome bridge controls it.
4. If the host exposes OpenAI native computer use, run the `js` tool from `cua_repl` with the following arguments: `{"code":"var verificationApp = await cua.getApp('<exact Chromium.app path>');","title":"Inspect isolated verification browser"}`. This first entry point returns the supported API documentation and UI state. Inspect before acting; use `getAXState`, `setValue`, `click`, `pressKey`, `scroll` and `getScreenshot` according to that active documentation. The native app handle identifies an app, not a profile. Confirm the selected window URL/title and window-owner PID belong to this run before acting. Concurrent native runs require a proven per-window selector or distinct app identities; stop if the target is ambiguous. The pilot used native app controls; a matching browser bridge may be used only after verifying its tab and profile ownership.
5. Keep capture off during login. Follow the project’s authentication and routing instructions using the owned browser. Inspect the approved login destination and fields before entering credentials. Never print credentials or record the login. Confirm the local identity and correlate a benign authenticated request with the assigned backend log; a visible environment badge alone is insufficient.
6. Inspect required local feature flags, organization permissions and runtime images. Record prior values, enable only the required local gate, verify the outcome and restore it during cleanup. When the change depends on a runtime image or sandbox, verify the actual version and required libraries in the task environment.

## Drive and observe

Start capture after confirming ownership and any required focus-isolation check. When using the bundled host, create `<browser-run>/CAPTURE` to enable its page click and console logs. The direct background launch does not install those observers: record timed actions and measured targets explicitly, and inspect console failures through the owned browser connection when needed. Record action intent, expected/observed result and wall-clock milliseconds separately. Native clicks on browser chrome/extension surfaces need a target rectangle from the observed UI and a separately logged timestamp; label inferred centers. Never invent coordinates to imply an unobserved click. The automatic observer covers the top-level page only; iframe, sidebar and native-chrome actions need separately measured full-window targets. The host's page-event normalization assumes a standard unmaximized window; compare one measured click against a captured frame before rendering rings.

Batch deterministic actions, then inspect their result. Screenshot capture can invalidate shared accessibility indices: acquire fresh state after screenshot-only observations. Keep full private snapshots when useful, but return only the relevant section/controls to the model. Avoid repeatedly dumping long navigation trees or full tracing payloads. Validate actual downloads through `downloads.ndjson` and files, not just a completed toast. A missing/empty download is a failed evidence step.

Record app errors and correlate the action with the backend request/trace and persisted effect. Show reload/persistence and real file contents where relevant. Distinguish feature verification from a separate sidebar-control capability test.

For the bundled host, stop by writing `<browser-run>/STOP` and await `stopped.json`; it closes only its context. For the macOS flow, follow its owned-process and virtual-display cleanup. Remove its ephemeral profile after downloads are retained; leave other browser sessions intact.

References: [Playwright persistent contexts](https://playwright.dev/python/docs/api/class-browsertype#browser-type-launch-persistent-context), [extensions](https://playwright.dev/docs/chrome-extensions), [OpenAI computer use](https://developers.openai.com/codex/app/computer-use). Tool APIs are supplied by the installed computer-use server, not inferred from these overview pages.

The [local virtual-display tests](local-display-test.md) distinguish extension-menu opening from ongoing sidebar interaction. Verify application-specific controls on each run; the capability fixture is not feature evidence.
