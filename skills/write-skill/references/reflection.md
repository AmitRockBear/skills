# Reflection

Inputs are the requested time window or supplied sessions, direct user corrections and the current instructions that own the behavior. Output is a prioritized proposal with evidence, exact replacement text, expected benefit and a proportionate validation plan.

1. Find direct corrections in the requested scope and compare them with the current owning instruction; distinguish events before and after its latest update.
2. Classify each failure as a missing instruction, a missed skill invocation, an ignored existing instruction or a tool limitation before proposing a fix.
3. Corroborate an inferred standing preference across separate tasks or dates; treat explicit enduring preferences as instructions and one-off overrides as local.
4. Propose the smallest replacement, removal, trigger correction or executable check in the existing owner. Cite the supporting events and the instruction replaced; use no change when the current rule already addresses the evidence.
5. For behavioral workflow changes, compare old and proposed instructions on the same representative task and relevant environment when feasible; record actual outcomes and limitations. For explanations and style, use user feedback rather than an invented benchmark.
6. Draft-only requests produce separate artifacts. Apply changes only within the user's authorized scope; update affected examples, caller contracts, links and invocation metadata together.

Example: if an explicitly requested review skill was skipped despite a correct trigger, diagnose that missed invocation before adding another code-quality paragraph.
